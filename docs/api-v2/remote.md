# Удалённые данные и `HTTP`-запросы

[Публичный контракт](../api-v2.md) · [Таблица](../data-table.md)

В режиме `source="remote"` таблица получает готовую выборку с сервера.
Локальная сортировка и поиск к ответу не применяются. Сервер обрабатывает
поисковый запрос, фильтры, сортировку и пагинацию.

## Структура ответа

Адаптер ответа возвращает `BuiltResponse<T>`:

```json
{
  "items": [{ "id": 1, "name": "Анна" }],
  "total": 100,
  "filtered": 40
}
```

| Поле       | Содержание                                                               |
| ---------- | ------------------------------------------------------------------------ |
| `items`    | Массив записей текущей страницы                                          |
| `total`    | Количество записей до фильтрации                                         |
| `filtered` | Количество записей после фильтрации; при отсутствии используется `total` |

Нормализованный результат `TableData<T>` всегда содержит все три поля.
Для `total` и `filtered` допустимы неотрицательные безопасные целые числа.
Значение `filtered` не может превышать `total`.

При `pagination=true` длина `items` не превышает `filtered` и `perPage`.
При `pagination=false` сервер возвращает весь результат: длина `items`
должна равняться `filtered`.

Все записи должны иметь допустимые уникальные ключи `rowKey`.
Неправильный `JSON`, результат адаптера, счётчики или ключи рассматриваются
как ошибка запроса и передаются через `requestError`.

### Коррекция страницы

После удаления или фильтрации записей текущая страница может оказаться за
пределами нового количества страниц. Для такой ситуации допустим пустой ответ.
Таблица ограничивает номер страницы и отправляет один корректирующий запрос.

Первая попытка завершается `requestSuccess` и `requestEnd` со статусом `success`.
Затем отправляются `update:page` и новый запрос с другим `requestId`.
Если и второй ответ не позволяет получить допустимую страницу, отображается
ошибка; третий корректирующий запрос не создаётся. Данные заменяются только
окончательным актуальным результатом.

## Контекст запроса

`requestAdapter` получает `RequestContext`: `url`, `pagination` и `requestBody`.
Поля тела формируются из эффективного состояния таблицы:

| Поле            | Правило                                                                                   |
| --------------- | ----------------------------------------------------------------------------------------- |
| `page`          | Текущая страница; отсутствует при отключённой пагинации                                   |
| `perPage`       | Размер страницы; отсутствует при отключённой пагинации                                    |
| `search`        | Поисковая строка без пробелов по краям; отсутствует при пустом запросе или `search=false` |
| `sortBy`        | Серверное имя `sortField` либо `field`; отсутствует без сортировки                        |
| `sortDirection` | `asc` или `desc`; отсутствует без сортировки                                              |
| `filter`        | `JSON`-совместимый объект; по умолчанию `{}`                                              |

Сортировка пользовательской колонки определяется её ключом в `sort.by`,
но сервер получает имя `sortField` или `field`.

## Адаптеры

`RequestAdapter` синхронно преобразует `RequestContext` в `BuiltRequest`.
`ResponseAdapter<T>` синхронно преобразует `JSON` типа `unknown` в `BuiltResponse<T>`.
Асинхронные адаптеры не входят в контракт.

Стандартные функции `defaultRequestAdapter` и `defaultResponseAdapter`
работают без плагина. Замена допускается через параметры таблицы или плагина;
параметр конкретной таблицы имеет приоритет.

Адаптер ответа отвечает за преобразование и проверку пользовательской схемы.
После него таблица проверяет структуру результата, количество записей и ключи.
Пример собственного запроса `GET` приведён в [руководстве по миграции](../migration-guide.md).

## Параметры `HTTP`-запроса

| Поле `BuiltRequest` | Тип                                 | Значение по умолчанию       |
| ------------------- | ----------------------------------- | --------------------------- |
| `url`               | `string`                            | Обязательный непустой адрес |
| `method`            | `GET` или `POST`                    | `POST`                      |
| `headers`           | `Record<string, string>`            | `{}`                        |
| `requestBody`       | `JSON`-совместимое значение         | `undefined`                 |
| `credentials`       | `omit`, `same-origin` или `include` | `same-origin`               |

Стандартный адаптер сохраняет адрес и отправляет `requestBody` методом `POST`.
Тело сериализуется через `JSON.stringify`. Заголовок `Content-Type: application/json`
добавляется только при наличии тела и отсутствии пользовательского заголовка.
Имена заголовков сравниваются без учёта регистра.

Для `GET` адаптер самостоятельно формирует строку запроса через `URL` или
`URLSearchParams` и возвращает адрес без `requestBody`. Тело запроса `GET`
считается ошибкой.

`FormData`, потоки, бинарные тела, методы `PATCH`/`PUT`/`DELETE` и произвольная
замена сетевого транспорта не поддерживаются. Транспорт таблицы предназначен
для чтения данных.

### `CSRF` и внешние адреса

`csrfToken` из конфигурации приложения добавляется как `X-CSRF-TOKEN` только
для `POST` к тому же источнику в браузере. Заголовок, явно заданный адаптером,
имеет приоритет. Токен автоматически не передаётся внешнему источнику.
Для запросов к внешним адресам `credentials` и заголовки задаются адаптером.

## Когда выполняется запрос

| Действие                                                       | Запуск                                                |
| -------------------------------------------------------------- | ----------------------------------------------------- |
| Первое подключение компонента в браузере                       | Сразу после подключения                               |
| Изменение страницы, размера страницы, сортировки или источника | Сразу после применения состояния                      |
| Изменение поиска или `filter`                                  | После задержки `300 мс`                               |
| Вызов `reload()`                                               | Сразу, независимо от совпадения с предыдущим запросом |
| Изменение выбора, плотности или оформления                     | Запрос не выполняется                                 |

Несколько изменений за один цикл обновления объединяются. Отложенная операция
отменяется при переходе к немедленному запросу. Контекст формируется по самому
новому эффективному состоянию.

Эквивалентные контекст и адаптеры не запускают повторный запрос, если такой
запрос уже выполняется или его успешный результат отображается. После ошибки
повтор допускается. Смена ссылки на функцию адаптера сбрасывает сохранённый
контекст. `reload()` принудительно обходит эту проверку.

## Загрузка и сохранение прежних строк

При первой загрузке строк ещё нет: отображается отдельное состояние `loading`.
При повторном запросе существующие строки сохраняются, а содержимое ячеек
скрывается за анимированными полосами. Геометрия таблицы не меняется.

Слот `loading` заменяет всю область строк, в том числе при наличии данных.
Во время загрузки выбор и действие по клику на строку недоступны.
Поиск, сортировка и пагинация могут запустить заменяющий запрос.

Смена `source` или `url` очищает прежние записи. При ошибке прежние строки
скрываются и отображается `error`. Тихое фоновое обновление и встроенный поллинг
не предусмотрены; обычный `reload()` использует то же состояние загрузки.

## Отмена и события

Каждая попытка получает возрастающий `requestId` в пределах экземпляра таблицы.
Новый запрос отменяет предыдущий. Только актуальная попытка может записать
данные, ошибку и состояние загрузки; запоздавший ответ не применяется.

| Результат попытки                                                  | События                                                                                          |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Запрос успешно построен и выполнен                                 | `requestStart` → `requestSuccess` → `requestEnd` со статусом `success`                           |
| Ошибка сети, `HTTP`, `JSON` или адаптера ответа                    | `requestError` → `requestEnd` со статусом `error`; ранее отправленный `requestStart` сохраняется |
| Ошибка контекста или адаптера запроса до построения `BuiltRequest` | `requestError` → `requestEnd` со статусом `error`, без `requestStart`                            |
| Отмена запущенной попытки                                          | Только `requestEnd` со статусом `aborted`                                                        |
| Отмена задержки до запуска попытки                                 | События не отправляются                                                                          |

После уничтожения компонента работа отменяется, последующие события не отправляются.
Метод `reload()` завершается при успехе, ошибке или отмене и не отклоняет
`Promise` из-за ошибки транспорта; ошибки представлены состоянием и событиями.

## Серверный рендеринг

Удалённая загрузка и задержка поиска запускаются только после подключения
компонента в браузере. На сервере выводится исходное пустое состояние без
сетевых событий. Автоматическая загрузка удалённых данных на сервере и
передача заранее загруженного удалённого результата не входят в `2.0`.

Конфигурация создаётся отдельно для каждого приложения и запроса серверного рендеринга.
Локальный режим отличается: его записи и колонки могут быть отрисованы на сервере.
